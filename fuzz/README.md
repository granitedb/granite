# Fuzz targets

Coverage-guided fuzz targets for every decoder and codec. See `docs/06-testing-and-engineering.md`.

This directory is its own Cargo package, outside the root workspace, because fuzzing needs a nightly toolchain and cargo-fuzz:

```bash
rustup toolchain install nightly
cargo install cargo-fuzz --locked
cd fuzz
cargo +nightly fuzz run <target> -- -max_total_time=<seconds>
```

Each target's corpus is in `corpus/<target>/`, committed after every gate run; cargo-fuzz reads and extends it. A fuzz gate of H CPU-hours (`docs/tasks/README.md`) is H hours of one process, or less with `-fork=<n>` across n cores.

| Target | What it checks |
|---|---|
| `catalog_decode` | `granite_schema::Catalog::decode` on arbitrary bytes never panics, and what it accepts encodes back to the same bytes. The corpus grew from the golden catalog of `crates/schema/src/tests.rs`. |
| `schema_compile` | `granite_schemac::compile` on arbitrary bytes never panics or hangs, and what it accepts prints as text that compiles to the same bytes. Run with `-max_len=1048576` (one message, the input bound of T1.4.5's gate). The corpus grew from `schemas/exchange.schema` and a schema using every form of the grammar. |
| `program_decode` | `granite_txn::Program::decode` on arbitrary bytes never panics, and what it accepts encodes back to the same bytes. Run with `-max_len=1048576` (one message) and `-malloc_limit_mb=2`, so any allocation of 2 MiB or more fails the run (the bound of document 03 section 5.1); recursion is bounded by the depth limit, and a deep input that overflowed the stack would crash. The corpus grew from the golden program of `crates/txn/tests/ir.rs`, one input per opcode and literals of several types. |
| `program_compile` | `granite_schemac::compile_program` on arbitrary bytes never panics or hangs, and what it accepts prints as text that compiles to the same IR, and reports without panicking. The catalog holds the tables of the validator tests. Run with `-max_len=1048576` (one message). The corpus grew from the reference program `schemas/bank/transfer.program` (its tables are not in the catalog, so it seeds the error paths), a program using every form of the grammar and one program per error case of `crates/schemac/tests/program.rs`; T5.2.6 added two programs with `on` sections, one annotated `independent`. |
| `program_validate` | `granite_txn::Program::validate` on every tree `Program::decode` accepts from arbitrary bytes never panics, gives the same answer twice, and what it accepts reads and writes at most `program_accesses_max` rows and names partition keys of the right length; `Program::classify` on it never panics (added by T5.2.6). The catalog holds the tables of the validator tests (`crates/txn/tests/support`), compiled from schema text. Run with the flags of `program_decode`. The corpus grew from the 50 programs of `crates/txn/tests/corpus.rs` (its ignored test `write_fuzz_seeds` writes them). |
| `fragment_decode` | `granite_query::Fragment::decode` on arbitrary bytes never panics, and what it accepts encodes back to the same bytes. Run with `-max_len=1048576` (one message) and `-malloc_limit_mb=2`, so any allocation of 2 MiB or more fails the run (the bound of document 05 section 4, the same as the program decoder's); recursion is bounded by the depth limit. The corpus grew from the fragments of `crates/query/tests/validate.rs` (its ignored test `write_fuzz_seeds` writes them). |
| `fragment_validate` | `granite_query::Fragment::validate` on every tree `Fragment::decode` accepts from arbitrary bytes never panics, gives the same answer twice, and what it accepts has one memory bound per operator and the scan, whose sum is its total, within `fragment_memory_max`. The catalog holds the table of the validator tests, compiled from schema text. Run with the flags of `fragment_decode`. The corpus grew from the same seeds. |
